# Multi-agent overview（LangChain）

官方文档：[Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)

## 1 核心定位：多agent不是默认选项，是权衡后的选择

开篇明确说：多agent系统协调专门化组件处理复杂工作流，**但不是每个复杂任务都需要这样做**——配上正确工具和提示词的单个agent往往能达到相近效果。官方建议：如果想要开箱即用的多agent支持，直接用**Deep Agents**（基于LangChain的高级框架，内置子agent/技能/规划/虚拟文件系统/上下文管理）。

## 2 为什么要用多agent——三个真实诉求，不是"看起来高级"

开发者说"需要多agent"时，通常在追求下面三者之一：

- **上下文管理**：给专业知识、但不撑爆模型的context window。如果上下文无限、延迟为零，直接把所有知识倒进一个prompt就行——现实不是这样，所以需要有选择地呈现相关信息的模式。
- **分布式开发**：让不同团队独立开发维护各自的能力，再用清晰的边界组合成更大系统。
- **并行化**：给子任务各自派一个专门的worker，并发执行，加快出结果的速度。

原文特别强调的三个"多agent特别有价值"的场景：单个agent工具太多、选哪个工具的决策做不好；任务需要带着大量上下文的专业知识；需要强制的顺序约束（解锁某个能力必须先满足某个条件）。

**这一节最重要的一句定性**："多agent设计的中心是**上下文工程**——决定每个agent看到什么信息。系统质量取决于确保每个agent获得其任务所需的正确数据。"——多agent架构选型，本质上是在做上下文工程的选型，不是纯粹的"任务分工"问题。

## 3 五种主要模式——一张表先建立全貌

**先说明一处命名调整**：官方原文把下表第三行叫"Skills"，但这个模式本质上**只有一个agent**，不涉及多个agent协作——为了避免跟真正的多agent模式（Subagents/Handoffs/Router）混为一谈，这份笔记里把它统一改名为**"单agent多Skills"**，跟`Skills.md`那一章学过的Claude Skills是同一个概念（按需加载打包好的专门指令/知识）。这里先说清楚为什么它依然被放进"multi-agent"这篇文档里——见第117行"值得记的点"第二条。

| 模式 | 工作原理 |
|---|---|
| **Subagents（子agent）** | 主agent把子agent当工具协调，**所有路由都经过主agent**，由它决定何时、怎么调用每个子agent |
| **Handoffs（切换）** | 行为随状态动态改变，工具调用更新状态变量，触发路由/配置变更，切换活跃agent或调整当前agent的工具和提示词 |
| **单agent多Skills** | 专门的提示和知识**按需加载**，**始终只有一个agent**，全程保持控制权，只是按需从技能库加载上下文 |
| **Router（路由器）** | 一个路由步骤对输入分类，指向一个或多个专门agent，结果被合成为一份合并响应 |
| **Custom workflows（自定义工作流）** | 用LangGraph搭建定制执行流，混合确定性逻辑和agent行为，把其他模式当节点嵌进工作流里 |

**模式选择指南（★数量表示强弱，1-5星）**：

| 模式 | 分布式开发 | 并行化 | 多跳（能不能连续调用多个子agent） | 直接用户交互 |
|---|:---:|:---:|:---:|:---:|
| Subagents | ★★★★★ | ★★★★★ | ★★★★★ | ★ |
| Handoffs | - | - | ★★★★★ | ★★★★★ |
| 单agent多Skills | ★★★★★ | ★★★ | ★★★★★ | ★★★★★ |
| Router | ★★★ | ★★★★★ | - | ★★★ |

**这张表最直观的信息**：Subagents在"分布式开发/并行化/多跳"三项都是满分，但"直接用户交互"只有1星（子agent的结果要经过主agent转手，不直接面对用户）；Handoffs和单agent多Skills恰好在"直接用户交互"这一项满分（因为控制权/上下文都留在同一个能直接面对用户的agent身上——单agent多Skills本来就只有一个agent，这一项天然满分）；Router强在并行化，但完全不支持多跳（一次分类分发，没有"连续调用"这个概念）。

**这五种模式可以混用**，原文举例：Subagents架构里的子agent可以调用工具去触发一个自定义工作流或router agent；子agent自己内部甚至可以再用"按需加载Skills"这个思路去管理自己的上下文。

## 4 性能对比——用三个具体场景，把"模型调用次数"和"token消耗"量化出来

这一节是这篇文档里最有价值的部分：**不是空谈"哪个模式更好"，而是拿同一个任务在四种模式下实际跑一遍，数模型调用次数和token消耗**。两个关键指标：**模型调用次数**（更多调用=更高延迟+更高单次请求API成本）、**处理的token总量**（更多token=更高处理成本+更容易碰到上下文上限）。

### 4.1 单次请求场景——用户说"买咖啡"

| 模式 | 模型调用次数 | 最佳匹配 |
|---|:---:|:---:|
| Subagents | 4 | |
| Handoffs | 3 | ✅ |
| 单agent多Skills | 3 | ✅ |
| Router | 3 | ✅ |

**关键洞察**：Handoffs、单agent多Skills、Router对单个任务最有效（各3次调用）；**Subagents多花一次调用，因为结果要流回主agent**——这一次额外开销换来的是集中控制。

### 4.2 重复请求场景——同一对话里连续两轮都说"买咖啡"

| 模式 | 第二轮调用次数 | 两轮总计 | 最佳匹配 |
|---|:---:|:---:|:---:|
| Subagents | 4 | 8（4+4） | |
| Handoffs | 2 | 5（3+2） | ✅ |
| 单agent多Skills | 2 | 5（3+2） | ✅ |
| Router | 3 | 6（3+3） | |

- **Subagents按设计是无状态的**——每次调用都从头走一遍完整流程，主agent维护对话上下文，但子agent每次都是一张白纸，第二轮跟第一轮一样贵。
- **Handoffs和单agent多Skills在第二轮省了一次调用**——因为咖啡agent/技能上下文在第一轮之后**仍然处于活跃状态**（状态持久化），第二轮不需要重新切换/重新加载，直接调工具+回复用户两步就够了。
- **Router依然要重新分类**——路由器按设计是无状态的，每个请求都要走一次LLM路由调用，所以第二轮还是3次（路由1次+调工具1次+回复1次）。

**关键洞察**："有状态模式（Handoffs、单agent多Skills）在重复请求上节省40-50%的调用；Subagents维持一致的单次请求成本——这种无状态设计提供强上下文隔离，代价是重复的模型调用。"

### 4.3 多领域场景——"比较Python/JavaScript/Rust在网页开发中的应用"

每种语言的agent/技能各自带约2000 token的文档，所有模式都能并行工具调用：

| 模式 | 模型调用次数 | 总token | 最佳匹配 |
|---|:---:|:---:|:---:|
| Subagents | 5 | ~9K | ✅ |
| Handoffs | 7+ | ~14K+ | |
| 单agent多Skills | 3 | ~15K | |
| Router | 5 | ~9K | ✅ |

- **Subagents**：每个子agent独立工作，只带着跟自己相关的上下文，总共9K token。
- **Handoffs**：**只能顺序执行**，没法并行研究三种语言，越切换对话历史越长，开销跟着涨，7+次调用、14K+ token。
- **单agent多Skills**：调用次数少（3次），但**每次后续调用都要处理全部6K token的技能文档**——因为技能一旦加载，后面每一步都带着它，token反而是四种模式里最高的（15K），子agent因为上下文隔离，处理的token量比它少67%。
- **Router**：用LLM做路由，之后并行调用agent，效果类似Subagents但多一个显式的路由步骤，9K token。

**关键洞察**："对于多领域任务，支持并行执行的模式（Subagents、Router）最有效。单agent多Skills调用次数少但token使用量高，因为上下文在累积。Handoffs在这里效率低——必须顺序执行，无法用并行工具调用同时咨询多个领域。"

### 4.4 汇总——一张表看清四种模式在三种场景下各自的账

| 模式 | 单次请求 | 重复请求 | 多领域 |
|---|:---:|:---:|:---:|
| Subagents | 4次调用 | 8次调用(4+4) | 5次调用，9K token |
| Handoffs | 3次调用 | 5次调用(3+2) | 7+次调用，14K+ token |
| 单agent多Skills | 3次调用 | 5次调用(3+2) | 3次调用，15K token |
| Router | 3次调用 | 6次调用(3+3) | 5次调用，9K token |

**按优化目标对号入座**：

| 优化目标 | Subagents | Handoffs | 单agent多Skills | Router |
|---|:---:|:---:|:---:|:---:|
| 单次请求 | | ✅ | ✅ | ✅ |
| 重复请求 | | ✅ | ✅ | |
| 并行执行 | ✅ | | | ✅ |
| 大上下文领域 | ✅ | | | ✅ |
| 简单聚焦任务 | | | ✅ | |

**这张表最值得记住的规律**：**"有状态"（Handoffs/单agent多Skills）省的是"重复请求"场景下的调用次数，"无状态+隔离"（Subagents/Router）省的是"多领域大上下文"场景下的token总量**——没有一种模式是全场景最优的，选型必须先想清楚自己的任务更接近哪一种场景。

## 值得记的点

- **这篇文档最大的价值不是介绍了新概念（五种模式里Subagents/Handoffs/Router在别的文档里都见过），而是第一次给出了可量化的性能对比方法论**——用同一个任务在不同模式下实际数调用次数和token量，而不是停留在"各有优劣"这种定性描述。
- **"单agent多Skills"这个模式本身不涉及多个agent，被放进"multi-agent"这篇文档里，理由不是分类错误，是这篇文档对"multi-agent"的定义比字面意思宽**——它指的其实是"当单个朴素agent的上下文/能力撑不住任务复杂度时，有哪些应对策略"，"真的多派几个agent"和"只留一个agent、但按需加载不同专门知识包"是回答同一个问题的两种不同策略，所以文档把它们放进同一张选型表、同一套性能对比里横向比较。这个概念本身跟`Skills.md`那一章学过的Claude Skills是同一个思路（按需加载打包好的专门指令/知识），这里是在"要不要上多agent"这个决策语境下重新审视它，当成一个更轻量的替代选项。
- **"多领域场景"里单agent多Skills反而token消耗最高**这个结论有点反直觉——因为技能一旦加载就会持续存在于后续每一次调用的上下文里，不像子agent那样调用完就释放；这提醒了一个容易被忽略的点：**"按需加载"解决的是"要不要一开始就背上"这个问题，不解决"背上之后要不要一直背着"这个问题**，后者需要额外的上下文管理（比如加载完就主动清掉，或者压根换成隔离式的子agent模式）。
