# Agent Teams（Claude Code）

官方文档：[Orchestrate teams of Claude Code sessions](https://code.claude.com/docs/en/agent-teams)

**先说结论**：Agent Teams是Claude Code里一个**实验性**功能（默认关闭，需要设置环境变量`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`才能用），跟Subagents是两套完全不同的协作模型——Subagents是"主agent派活、子agent干完汇报"的单向委托，Agent Teams是"多个独立Claude实例互相发消息、抢共享任务列表"的对等协作。这正好是用户问到的"agent team架构"，跟Anthropic那篇研究博客里讲的subagent架构不是一回事，是Claude Code产品层面单独在做的另一套东西。

## 1 跟Subagent的关键区别

官方原文一句话概括区别："Subagents report results back to the main agent. In agent teams, teammates share a task list, claim work, and communicate directly with each other."

官方对比表：

| 维度 | Subagents | Agent Teams |
|---|---|---|
| **上下文** | 有自己的context window；结果返回给调用者 | 有自己的context window；完全独立 |
| **通信** | 向调用者返回一个结果；如果Claude在派发时给子agent起了名字，子agent之间也能互相发消息 | 队友之间直接互相发消息 |
| **协调** | 主agent管理全部工作 | 队友之间通过消息自我协调，另外有Task工具的agent还有共享任务列表 |
| **最适合** | 只关心结果的聚焦型任务 | 需要讨论和协作的复杂工作 |
| **Token成本** | 更低：结果被摘要后返回主上下文 | 更高：每个队友都是一个独立的Claude实例 |

**这张表最关键的一点是"通信"这一行**：Subagent架构里，子agent默认只能"打工人向老板汇报"——结果单向流回调用者；只有当Claude主动给子agent起了名字（named subagent），子agent之间才能互相发消息，这已经是Subagent机制里"最像团队"的一个例外情况了。Agent Teams直接把这个例外变成常态：队友之间的直接通信是设计的核心，不再依赖"起名字"这个变通手段。

**什么时候该用哪个**：官方原文——用Subagents处理"只要结果、不需要讨论"的聚焦型任务；用Agent Teams处理"需要队友之间互相分享发现、互相挑战、自主协调"的复杂工作。Agent Teams协调开销更大、token消耗显著更高，只有并行探索能带来真实价值时才值得用；顺序性任务、同文件编辑、依赖关系多的工作，单session或Subagents效果更好。

## 2 架构组成

官方定义了四个组件：

| 组件 | 角色 |
|---|---|
| **Team lead** | 主Claude Code会话，负责创建团队、派生队友、协调工作 |
| **Teammates** | 各自独立的Claude Code实例，各自领取分配到的任务 |
| **Task list** | 队友可以领取和完成的共享工作项列表 |
| **Mailbox** | agent之间通信用的消息系统 |

### 2.1 Mailbox——每个agent一个JSON文件

每个agent的邮箱是一个JSON文件，路径`~/.claude/teams/{team-name}/inboxes/{agent-name}.json`。Claude Code每次读邮箱文件时都会校验每一条记录，格式不对的条目会被当错误上报并从文件里删掉，但格式正确的消息照常送达（v2.1.207之前，一条格式错误的记录会导致每秒重复报错，并且卡住整个邮箱的投递，直到手动删文件才能恢复——这个bug后来修了）。

只有当"写入接收方邮箱文件"这个动作本身成功了，Claude Code才会告诉发送方"消息已发送"——不管是纯文本消息还是结构化的协议消息（比如plan审批请求、关闭请求）。写入失败（比如磁盘满了、邮箱目录不可写），发送方会收到一个错误，且这条消息真的没发出去。

### 2.2 Task list——文件锁防止竞态

任务有三种状态：pending（待办）、in progress（进行中）、completed（已完成）；任务之间可以有依赖关系，一个还有未完成依赖的pending任务不能被认领，等依赖的任务完成后会自动解锁（不需要人工干预）。

两种认领方式：**lead主动分配**（告诉lead把某个任务派给某个队友）或**队友自己抢**（队友做完手头的任务后，自己去挑下一个没人认领、也没被依赖卡住的任务）。

**认领机制用的是文件锁，防止多个队友同时抢同一个任务时出现竞态条件**——这是这份文档里唯一明确提到"锁"这个词的地方，用的是最朴素的文件锁，不是数据库事务或分布式锁。

### 2.3 团队和任务存在哪、什么时候清理

团队和任务用"session派生出来的名字"存在本地：名字是`session-`加上session ID的前8个字符。

- **团队配置**：`~/.claude/teams/{team-name}/config.json`
- **任务列表**：`~/.claude/tasks/{team-name}/`

这两份都是session启动时自动生成、随着队友加入/闲置/离开自动更新的。**团队配置目录在session结束时会被删掉**；**任务列表目录会留在本地、且从不上传**，所以恢复（resume）一个session时任务还在——留存周期跟已经学过的`cleanupPeriodDays`（session transcript清理策略）是同一套规则。

## 3 权限模型——队友不能替你做安全决策

队友一开始继承lead的权限设置（如果lead开了`--dangerously-skip-permissions`，所有队友也是）；派生之后可以单独改某个队友的模式，但派生那一刻不能单独指定。

队友的权限确认提示会冒泡到lead会话里，由你在lead那边批准（**plan审批是设计上唯一的例外**——lead会话会自动批准队友的plan，不会再单独弹一次确认给你）。

**agent之间发消息这件事，有一条专门的安全边界**：当一个agent通过`SendMessage`给另一个agent发消息时，Claude Code会明确告诉接收方"这条消息来自另一个Claude会话，不是来自你（人类用户）"——一个队友**不能**替你批准权限提示、也不能代你给出同意；一个被拒绝了某个操作的队友，也**不能**把这个请求转发给另一个队友来绕过检查。在auto模式下，分类器对agent间消息还多做两层检查：把"另一个agent转述的批准声明"当成不可信输入而不是你本人的确认；每条消息投递前都会先审查一遍，挡下来的消息永远到不了接收方。

**这一点值得跟`TurnLoop.md`的Handoff/Human-in-the-loop讨论连起来看**：多agent协作一旦引入"agent之间可以互相发消息"这个能力，就必须同步引入"防止agent互相伪造用户授权"这道防线——这是Agent Teams比单纯Subagent多出来的一类新风险面，Subagent因为通信路径单向（只能向调用者汇报），不存在"两个平级agent互相传递未经验证的授权声明"这个问题。

## 4 Context与通信机制

每个队友有自己独立的context window。派生时，队友会加载和普通session一样的项目上下文（CLAUDE.md、MCP servers、skills），外加lead给的派生提示词（spawn prompt）——**但lead自己的对话历史不会传给队友**，队友是从零开始的。

四种信息共享方式：

1. **消息自动投递**：队友发消息会自动送达，lead不需要轮询。
2. **闲置通知（idle notification）**：队友做完任务停下来时，会自动通知lead——**但这条通知不包含队友的产出内容**，队友要把结果告诉lead，得靠主动发消息或者更新共享任务列表这两种方式之一，通知本身只是个"我停下来了"的信号。
3. **共享任务列表**：有Task工具的agent能看到任务状态、认领可用的工作。
4. **队友消息**：按名字给某个特定队友发消息；要通知所有人，得给每个接收者各发一条。

## 5 Token成本——显著更高，且线性增长

官方原文明确警告：Agent Teams用的token比单session显著更多，因为每个队友都有自己独立的context window，token消耗随活跃队友数量增长。研究/评审/新功能开发这类场景，多花的token通常值得；常规任务用单session更划算。

## 6 使用场景与最佳实践（精简摘录）

官方给的三个典型场景：①并行代码评审（三个队友各自专注安全/性能/测试覆盖率三个不同维度，同时评审同一个PR，lead最后综合三方发现）；②多假设并行调试（5个队友各自带着不同假设去调查同一个bug，并且互相尝试推翻对方的理论，像科学辩论一样收敛到最可能的根因——官方特别强调这种"对抗式"设计能对抗"单agent找到一个说得过去的解释就停止深挖"的锚定效应）；③跨层协调（前端/后端/测试分别由不同队友负责）。

最佳实践里比较值得记的几条：**团队规模建议从3-5个队友起步**（token成本线性增长+协调开销递增+边际收益递减三重因素叠加，规模不是越大越好）；**任务粒度要"刚刚好"**（太小协调开销超过收益，太大队友闷头做太久增加浪费风险，理想是"一个函数/一个测试文件/一次评审"这种有明确交付物的自包含单元）；**明确告诉队友要各自负责哪些文件**，避免两个队友同时改同一个文件互相覆盖。

## 7 已知限制（Limitations）——毕竟是实验性功能

这一节是这份文档里最值得记的部分之一，直接反映了这个功能目前的成熟度边界：

- **in-process队友不支持session恢复**：`/resume`和`/rewind`不会恢复in-process模式下的队友，lead可能会尝试给已经不存在的队友发消息——恢复session后如果发生这种情况，需要手动告诉lead重新派生队友。
- **任务状态可能滞后**：队友有时候没能正确把任务标记为完成，导致依赖它的任务被卡住，需要人工检查、手动更新状态或提醒lead去催队友。
- **关闭可能较慢**：队友会先完成当前请求/工具调用才关闭，可能要等一阵子。
- **一个session只能有一个团队**：不能建多个命名团队，也不能跨session共享同一个团队。
- **不支持嵌套团队**：**队友不能再派生自己的队友，只有lead能管理团队**——这是一条硬性架构约束，避免了失控的多级扇出。
- **in-process队友不能派生后台子agent**：一个队友自己派生的子agent只能在前台跑，因为队友的后台任务没法在lead进程退出后继续存活；队友尝试`background: true`会直接报错或者被强制改成前台静默运行。
- **lead身份固定**：主session在其生命周期内永远是lead，不能把某个队友提升为lead，也不能转移leadership。
- **权限只能在派生时继承**：所有队友派生时都继承lead当时的权限模式，派生之后可以单独改某个队友的模式，但派生那一刻不能逐个指定。

**"不支持嵌套团队"这条限制，直接呼应了OpenClaw`Sub-agents`文档里"严格两级嵌套深度限制"的设计**（Depth 2 agent禁止再调用`sessions_spawn`，防止失控扇出）——两家产品各自用不同的机制（Claude Code是"完全禁止队友二次派生"，OpenClaw是"允许到depth 2但depth 2是叶子节点"），解决的是同一类"多agent编排失控扇出"的风险，值得在这一章后面做各家对比时专门拎出来讲。

## 8 版本与稳定性提醒

**这份文档本身反复强调这是v2.1.178前后的实验性功能快照**：文中大量"As of v2.1.199""Before v2.1.207"这类版本标注，说明这个功能还在快速迭代、行为随版本变化——不是一个已经定型的稳定API，跟`TurnLoop.md`/`SessionPersistence.md`里读过的那些已经进入稳定文档的机制（Handoff、Sessions、Checkpointer）不是同一个成熟度级别，笔记里的具体细节（比如"闲置行30秒后隐藏"这类UI行为）有效期可能不长，重点应该放在架构层面的设计决策上，不用死记版本号细节。
