# An update on recent Claude Code quality reports 学习笔记

来源：Anthropic官方博客，发布于2026-04-23，地址 https://www.anthropic.com/engineering/april-23-postmortem 。本笔记不逐字翻译，是转述事件经过和论证逻辑，关键短句用引用块标出。

**这篇文章在本章的位置**：它不是一篇讲"怎么做parity/快照测试"的方法论文章，是一份**事故复盘**——用户反馈Claude变差了，Anthropic排查了一个月，发现是三个独立改动叠加造成的。这一章想从这篇里拿到的是"**动机**"：不做好parity测试，具体会摔在哪里、代价有多大，为后面"怎么做"的方法论提供一个真实、具体的反面参照。

## 1 背景：用户反馈变差，排查了一个月

过去一个月，Anthropic陆续收到用户反馈，说Claude的回复变差了。排查之后确认影响的是Claude Code、Claude Agent SDK、Claude Cowork三个产品面，**API本身没受影响**。最终定位到三个互相独立的改动，2026年4月20日（v2.1.116）全部修复。

文章开篇点出一个关键的诊断难点：

> Because each change affected a different slice of traffic on a different schedule, the aggregate effect looked like broad, inconsistent degradation.

翻译：因为这三个改动各自影响的是不同的一部分流量、上线的时间点也不一样，叠加在一起看起来就是一种笼统的、不一致的整体性能下降——这也是排查耗时一个月的原因之一：三月初就开始收到反馈，但一开始很难跟正常的用户反馈波动区分开，而且**内部日常使用和已有的evals一开始都没能复现出这些问题**。

## 2 问题一：默认reasoning effort的反复横跳

2月发布Opus 4.6时，Claude Code默认reasoning effort设成了`high`。上线后收到反馈：`high`模式偶尔会思考太久，导致界面看起来卡死，延迟和token消耗都不成比例地高。

Anthropic内部测试和评估显示，`medium`档位在多数任务上只掉一点点智能水平，但延迟明显更低，也没有`high`档偶发的长尾超长思考问题，还能帮用户更省usage limit——于是3月4日把默认值从`high`改成了`medium`。改完之后，用户很快反馈"Claude Code感觉变笨了"，尝试了几轮UI改进（启动提示、行内effort选择器、恢复ultrathink）想让用户注意到可以自己调整默认值，但大部分用户还是留在了`medium`默认值上。听取更多客户反馈后，4月7日撤销了这个改动，现在Opus 4.7默认`xhigh`，其他模型默认`high`。

## 3 问题二：一个缓存优化bug让Claude变"健忘"

Claude的推理过程正常会保留在对话历史里，方便它在后续每一轮都能看到自己之前为什么做了这些编辑和工具调用。3月26日上线了一个本意是提升效率的改动：会话闲置超过一小时后，清掉旧的thinking内容，减少恢复会话时的开销（因为闲置太久缓存本来就会失效，正好顺便裁掉不必要的未缓存token）。

**实现有bug**：本该只清一次，结果变成了这个会话剩余的每一轮都在清。会话一旦跨过闲置阈值一次，之后每次请求都被告知"只保留最近一块推理内容，之前的全部丢弃"——如果用户在Claude执行工具调用的过程中发消息打断，这条新指令甚至会波及当前这一轮的推理。Claude还在继续执行，但越来越不记得自己当初为什么做了这些选择——用户看到的就是健忘、重复、奇怪的工具选择。因为这个bug会持续导致缓存未命中，也顺带解释了另一批"usage limit消耗得比预期快"的反馈。

原文提到两个让这个bug一开始很难复现的干扰因素：一个跟消息排队相关的内部实验、以及一个跟thinking显示方式相关的改动，恰好在大多数CLI会话里掩盖了这个bug，导致连测试外部构建版本时都没抓到。这个bug**通过了多轮人工和自动代码审查、单元测试、端到端测试、自动化验证、以及内部试吃（dogfooding）**，因为只在"过期会话"这种边缘场景才触发、又很难复现，花了一周多才定位到根因。修复过程中，团队用Opus 4.7对着当初那批出问题的PR回溯跑了一遍Code Review工具——**在提供完整代码库上下文的情况下，Opus 4.7找到了这个bug，Opus 4.6没找到**。这个bug在4月10日（v2.1.101）修复。

## 4 问题三：一条system prompt指令伤到了代码质量

Opus 4.7相对上一代有个明显的行为特点——更啰嗦，这让它在难题上表现更聪明，但也会多产出很多token。Anthropic在Opus 4.7发布前几周开始为它调优Claude Code（每次发新模型前都要为这个模型单独优化harness和产品）。

减少啰嗦的手段有模型训练、prompting、改进思考过程的展示方式几种，团队都用上了，其中一条加进system prompt的指令造成了格外大的副作用：

> "Length limits: keep text between tool calls to ≤25 words. Keep final responses to ≤100 words unless the task requires more detail."

经过几周内部测试、跑过的那批evals没有发现回归，团队对这个改动有信心，4月16日跟着Opus 4.7一起上线了。事后调查时，团队又跑了更多消融实验（逐行删system prompt里的内容，看每一行各自的影响），换了一批更大范围的evals，**其中一项评估显示Opus 4.6和4.7的分数都掉了3%**——4月20日的发布里立刻撤销了这条prompt。

## 5 为什么这三个问题一开始都没被内部测出来

三个问题合起来暴露的是同一类漏洞：**内部测试环境和外部真实使用环境之间存在没被察觉的差异**——问题二里两个无关的内部实验偶然掩盖了bug；问题三里最初跑的那批evals没有覆盖到、后来换了更大范围的评估集才测出3%的下降；问题一和问题二都提到内部日常使用（dogfooding）没能复现问题。三个案例指向的都是同一件事：**"内部测试通过"不等于"外部真实build上表现一致"**——这正是parity测试要解决的核心问题。

## 6 后续会做哪些改变

原文给出的具体改进措施，逐条看跟parity/快照测试的关系都很直接：

- **让更多内部员工用跟外部完全一致的public build**（而不是内部专门用来测试新功能的版本）——这是在直接补上"内部环境跟外部环境不一致"这个漏洞，本质就是在提高内部测试环境和生产环境之间的parity。
- **改进内部用的Code Review工具**，并把改进后的版本同步给客户使用——呼应问题二里"Opus 4.7能查出Opus 4.6查不出的bug"这个发现。
- **给Claude Code的每一次system prompt改动，都跑一整套按模型分别验证的evals**，持续做消融实验搞清楚每一行的具体影响，还搭建了新工具方便审查和审计prompt改动。
- **在`CLAUDE.md`里加了指导，确保针对特定模型的改动只对目标模型生效**，不会误伤其他模型。
- **对任何可能牺牲智能水平换取其他收益的改动，加上soak period（观察期）、更大范围的eval套件、以及灰度发布**，让问题能更早被发现。

## 7 对parity测试的启示

这篇复盘没有给出一套parity测试的方法论，但用三个真实案例把"不做好parity测试会怎样"讲得很具体：

- **测试环境和生产环境不是一回事，哪怕两者理论上应该一样**——内部专门用来测新功能的build，跟用户手上跑的public build，只要有一丁点差异，就可能让一个真实存在的bug在内部怎么都测不出来。
- **"没有regression"这个结论本身要看eval套件的覆盖范围**——问题三里最初那批evals没查出3%的下降，不是因为分数真的没降，是因为一开始跑的评估集不够大，覆盖不到那个下降的维度。这跟《Demystifying evals》里"不能直接采信eval分数，除非有人真的深入看过细节"是同一个提醒的另一种呈现方式。
- **单个改动看起来风险很小，但会跟其他改动在用户端叠加**——三个问题各自影响不同的模型、不同的时间段，叠加起来才呈现为"广泛的、不一致的质量下降"，如果每个改动上线前都有更严格的parity验证和灰度机制，本可以在这个叠加效应形成之前就被拦下来。
