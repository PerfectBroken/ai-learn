# Set up LLM-as-a-judge online evaluators 学习笔记

来源：LangChain官方文档，地址 https://docs.langchain.com/langsmith/online-evaluations-llm-as-judge 。

**先说结论**：这篇文档篇幅很短（原文只有六个小节，没有一句方法论层面的论证），性质是一份**产品操作手册**（在UI里点哪个标签、填哪个字段），不是像《Demystifying evals》八步路线图那样的方法论文档。这个发现直接回应了上一轮的讨论——**"LangSmith官方对在线评估寥寥几笔"这个判断，读完这篇之后确认是站得住的**，我上一轮说"可能是我们没读到那篇更深的文档"这个保留意见，读完可以撤回了：这篇就是LangSmith官方在"在线评估怎么配置"这个问题上给出的最详细的文档，内容确实很薄，没有藏着更深的方法论。

本笔记不逐字翻译，是转述操作流程和其中少量真正带方法论性质的点。

## 内容概览

原文六个小节，前五个基本是纯操作步骤：在LangSmith UI的Tracing Projects页面下找到某个项目，点Evaluators标签，点+Evaluator创建一个评估器（可以从零建、复用workspace里已有的、或者从模板起步）——这是"新增在线evaluator"这一件事的点击路径，没有更多内容。

## 真正带方法论性质的几个点（值得单独记）

跳出UI操作细节，这篇文档里有四处内容，回答的是"设计一次在线评估该考虑什么"这个真正的问题，跟离线评估的关注点不一样：

**1）该给哪些run跑评估——用过滤条件圈定范围**：原文给了三类典型的过滤依据——用户主动给了负面反馈的run、调用了特定工具的run、匹配特定元数据的run（比如只评估企业客户的trace）。这是在回答"生产流量这么大，不可能全评，该优先评哪些"这个离线评估不需要面对的问题——离线评估的数据集本来就是提前精选好的有限集合，不存在"该评哪些"这个选择问题。

**2）采样率——控制成本的机制**：可以设定只对过滤后的一部分run跑评估（比如只跑10%），原文举的理由直接是"控制成本"。这也是在线评估独有的考量——离线评估的成本是一次性的（跑一遍测试集），在线评估只要生产流量不停，评估就要一直跑下去，成本是持续累积的，所以需要一个采样率这样的阀门。

**3）Backfill——对历史流量补跑规则**：新建一条评估规则时，可以选择"应用到过去的run"，指定一个起始日期，让这条新规则去回溯评估在这个日期之后已经发生过的历史流量，而不是只对新流量生效。

**4）Spend limit——按周设置的花费上限**：可以给某个evaluator挂的所有项目/数据集设置每周LLM花费上限，默认继承组织级别的限制，管理员可以针对某个evaluator单独覆盖。一旦达到这个限制，LangSmith会暂停这个evaluator，直到每周一UTC 0点限制重置，或者有人手动调高额度。这跟上面的采样率是同一类问题（持续运行的评估会持续花钱），只是从"控制评估覆盖率"换成了"给花费本身设一道硬顶"。

## 跟离线评估的本质差异

把这四点合起来看，在线评估真正独有、离线评估完全不需要考虑的问题只有一类：**怎么在一个不会停止、体量不可控的生产流量里，圈出一个负担得起的评估范围**（用什么规则过滤、采多大比例、要不要往回补、花多少钱封顶）。除此之外——具体怎么设计一个LLM-as-judge打分器、怎么处理多模态内容——这些跟离线评估用的技术是同一套，文档里也是直接链接回`llm-as-judge`那篇通用文档，没有为在线场景重新讲一遍。
