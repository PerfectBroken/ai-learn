# OWASP Top 10 for Agentic Applications 2026 学习笔记

来源：OWASP GenAI Security Project — Agentic Security Initiative，用户提供的PDF，2025年12月9日发布，CC BY-SA 4.0协议。主导人是John Sotiropoulos（OWASP GenAI Security Project Board Member）、Keren Katz（Tenable）、Ron F. Del Rosario（SAP），100+行业专家参与评审。本笔记不逐字翻译，是转述十条风险各自的定义、跟相邻条目的区分、代表性攻击场景和关键防护建议，短句用引用块标出。

**这份文档在行业里的位置**：跟通用的《OWASP Top 10 for LLM Applications》（LLM01-LLM10）是两份不同的文档——LLM Top 10测的是"单次模型调用"层面的风险（比如prompt injection、输出处理不当），这份Agentic Top 10（简称ASI，Agentic Security Initiative）测的是"agent会规划、行动、跨多步骤做决策"这个更高层级才会出现的风险。文档明确说自己不是要替代已有指南，是把OWASP GenAI Security Project已经发布的一整套更详细的指南（核心分类法《Agentic AI - Threats and Mitigations》、《Agentic Threat Modelling Guide》、《Securing Agentic Applications》、《State of Agentic AI Security and Governance》）浓缩成一份"可以直接上手用"的十条清单，每条都配了简短定义、常见漏洞例子、真实攻击场景、以及可执行的防护建议。

**开篇信里提的一个概念值得先记下**：Leaders letter里把"Least-Privilege"（最小权限）这个安全设计的老概念，往agent场景延伸出了一个新提法——**"Least-Agency"（最小自主权）**：

> deploying agentic behavior where it is not needed expands the attack surface without adding value

翻译：在不需要自主行为的地方部署agentic能力，只会扩大攻击面，不会带来任何额外价值。这条原则贯穿了后面十条风险里的很多防护建议——不是"给agent加更多约束"，是从一开始就反问"这个场景真的需要agent自主决策吗"。另外一条被反复强调的原则是**"strong observability becomes non-negotiable"**——没有清晰的可见性，看不到agent在做什么、为什么这么做、调用了哪些工具，微小问题会被悄悄放大成系统性故障。

## 十大风险总览图

文档在正文之前先给了一张系统级示意图，把十条风险按它们实际发生在agent系统的哪个环节做了分类，这个视角比单纯罗列十条名字更有用：

- **输入端（Inputs）**：用户prompt、API调用、外部agent接入，对应**ASI01**（目标劫持）、**ASI03**（身份权限滥用）、**ASI09**（人-agent信任滥用）——这几类风险的入口都在"外部东西进来的地方"。
- **处理/编排层（Integration/Processing）**：policy治理层、human-in-the-loop、agent之间的协作与通信，对应**ASI07**（agent间通信）、**ASI10**（失控agent，特别标出"agent互相协作时,其中一个变坏"这个场景）。
- **连接的数据源和记忆**：对应**ASI06**（记忆与上下文投毒）。
- **输出端（Outputs）**：工具调用、外部API/资源、外部agent，对应**ASI02**（工具滥用）。
- **贯穿全局、不属于某一个环节的**：**ASI04**（供应链漏洞）、**ASI05**（意外代码执行）、**ASI08**（级联故障）——这三类是系统级、跨环节的风险，图上专门用横跨底部的方式标出，提示它们不是"某一个点"的问题。

## ASI01: Agent Goal Hijack（agent目标劫持）

**核心定义**：agent具备自主执行一连串任务去达成目标的能力，但因为agent（以及底层模型）没法可靠区分"指令"和"相关内容"这两类输入，攻击者可以通过prompt操纵、伪造的工具输出、恶意构件、伪造的agent间消息、被投毒的外部数据等多种手段，操纵agent的目标、任务选择或决策路径。

**跟相邻条目的区分**（这是这份文档一个很有特色的写法，每条风险都会专门说清楚自己跟哪些相邻条目不一样，避免混淆）：跟通用LLM Top 10里的**LLM01:2025 Prompt Injection**不同——LLM01针对的是"单次模型响应被篡改"，ASI01针对的是"更广泛的agentic影响"——操纵后的输入会改变agent多步骤行为的走向，不只是影响一次回复。跟**ASI06**（记忆与上下文投毒）和**ASI10**（失控agent）也不同：ASI01是攻击者**直接**改变agent的目标/指令/决策路径（不管是交互式改的，还是通过文档、模板这类预先埋伏的输入间接改的）；ASI06针对的是**存储记忆的持续性腐化**；ASI10针对的是**没有攻击者主动控制、agent自己产生的自主性偏移**。

**代表性攻击场景**：**EchoLeak**——一次零点击间接prompt injection，攻击者发一封精心构造的邮件，静默触发Microsoft 365 Copilot执行隐藏指令，在用户毫不知情、没有任何交互的情况下，导致AI泄露机密邮件、文件和聊天记录。另一个是**Inception attack on ChatGPT**——一份恶意Google Doc给ChatGPT注入指令，诱导它把用户数据泄露出去，并说服用户做出考虑不周的商业决策。

**关键防护建议**：把所有自然语言输入（用户文本、上传的文档、检索到的内容）**一律当作不可信**，走跟LLM01同一套输入校验和prompt injection防护流程；给agent工具强制最小权限，高影响或改变目标的操作要求人工审批；把agent的system prompt定义清楚并锁定，目标优先级和允许的操作要显式、可审计；运行时同时校验用户意图和agent意图，出现目标偏移就暂停执行、留痕供审查；建立行为基线（目标状态、工具使用模式），持续监控偏差；定期做红队测试，专门模拟目标劫持场景。

## ASI02: Tool Misuse and Exploitation（工具滥用与利用）

**核心定义**：agent因为prompt injection、错位对齐、或者不安全的委托/模糊指令，滥用了本来合法的工具，导致数据外泄、工具输出被操纵或工作流被劫持。跟**LLM06:2025 Excessive Agency**相关，但LLM06关注的是"过度授权的自主权本身"，ASI02关注的是**已经在授权范围内的agent，把一个合法工具用出了不安全或非预期的方式**——比如删除有价值的数据、过度调用高成本的API、泄露信息。如果滥用涉及权限提升或凭证继承，归**ASI03**；如果滥用导致任意或被注入的代码执行，归**ASI05**；工具定义现在越来越多通过MCP server提供，这跟**ASI04**（供应链漏洞）也自然有交叠。

**代表性攻击场景**：**EDR Bypass via Tool Chaining**——一个安全自动化agent收到一条注入的指令，让它把几个本身合法的管理工具（PowerShell、cURL、内部API）串联起来外泄敏感日志，因为每条命令都是由受信任的可执行文件、用合法凭证执行的，主机端的监控（EDR/XDR）完全看不出任何恶意软件或漏洞利用的痕迹，滥用就这样藏过了检测。

**关键防护建议**：给每个工具定义最小权限画像（scope、速率上限、出站白名单），把这些画像做成IAM/授权策略，而不是靠临时的约定；高影响或破坏性操作要求显式的操作级认证和人工确认，执行前展示预执行计划或diff预览；工具/代码执行放进隔离沙箱，强制出站访问白名单；把LLM或planner的输出当作不可信，加一层"Intent Gate"式的策略执行中间件，校验意图和参数、强制schema、发放短期凭证；给工具用量设置成本/速率/token预算上限，超限自动撤销或限流；发放即时（just-in-time）、短期有效的凭证，绑定到具体session，用完即失效；对工具名称做语义和身份校验（"语义防火墙"），强制全限定名和版本锁定，避免工具别名冲突或被抢注的相似名字工具。

## ASI03: Identity and Privilege Abuse（身份与权限滥用）

**核心定义**：利用agent里的动态信任和委托机制，通过操纵委托链、角色继承、控制流、agent上下文（包括跨互联系统缓存的凭证或对话历史）来提权、绕过控制。这里的"身份"既指agent被赋予的persona，也指代表这个persona的任何认证材料（API key、OAuth token、被委托的用户session）。**根源是用户中心的身份系统和agentic设计之间的架构性错位**——没有一个独立、被治理的身份，agent就处在一个"归因空白"里，真正的最小权限根本没法强制执行。跟**ASI02**不同：ASI02是agent用自己已获得的权限、把一个工具用出了不安全的方式；ASI03是agent通过操纵委托和信任关系，获得了**本不该有**的权限。

**代表性攻击场景**：**Cross-Agent Trust Exploitation（Confused Deputy）**——一封伪造的邮件冒充IT部门，指示邮件分拣agent让财务agent转账；分拣agent转发这条指令，财务agent因为信任这是"来自内部agent"的请求，没有二次验证就处理了这笔欺诈付款。**Forged Agent Persona**——攻击者在内部的Agent2Agent注册表里注册了一个伪造的"Admin Helper" agent card，其他agent信任这个描述、把系统级维护任务派给它，攻击者控制的这个agent随即以"内部信任"的名义下发系统级命令。

**关键防护建议**：强制任务范围内的短期权限（每个任务单独发放窄范围、短期有效的token，用mTLS证书或有范围限制的token限制爆炸半径）；隔离agent的身份和上下文（每个session单独跑沙箱，任务之间清空状态）；对每一步高权限操作做集中式策略引擎的重复校验；对高权限或不可逆操作强制human-in-the-loop审批；把OAuth token绑定到一份签名的"意图声明"（主体、受众、目的、session），token使用范围跟当前请求的意图不匹配就拒绝；评估成熟的agentic身份管理平台，把agent当作有范围限制凭证、审计轨迹、生命周期管理的托管非人类身份来对待（举了Microsoft Entra、AWS Bedrock Agents、Salesforce Agentforce、Workday的ASOR模型、Google Vertex AI里正在出现的类似模式做例子）。

## ASI04: Agentic Supply Chain Vulnerabilities（agent供应链漏洞）

**核心定义**：当agent、工具、以及相关构件是由第三方提供、在传输过程中可能被恶意植入、篡改或攻陷时，就会出现agentic供应链漏洞。这些依赖既可能是静态的（模型和模型权重、工具、插件、数据集），也可能是动态的（agentic接口——MCP、A2A——agentic注册表和相关构件、更新渠道），可能给agent的执行链引入不安全代码、隐藏指令或欺骗性行为。跟通用**LLM03:2025 Supply Chain**的区别是：LLM03关注的是**静态**依赖；agentic生态系统经常在**运行时动态组合能力**（动态加载外部工具、动态生成agent persona），这种分布式的运行时协调、叠加上agent的自主性，制造出了一条能把漏洞级联到多个agent之间的"活的"供应链——问题的重心从"清单里有什么"转移到了"运行时组装出来的东西是不是安全、可信、可分享的"。

**代表性攻击场景**：**Amazon Q Supply Chain Compromise**——一个被投毒的prompt出现在VS Code的Amazon Q插件仓库v1.84.0版本里，在被发现前已经分发给了成千上万用户，展示了上游agent逻辑被篡改后是怎么级联、放大影响的。**Malicious MCP Server Impersonating Postmark**——被报告为npm上第一个"野生"发现的恶意MCP server，它冒充postmark-mcp这个包，暗中把邮件密送给攻击者。

> **真实机制细节（查证补充，2025年9月）**：Postmark（ActiveCampaign旗下）在GitHub上有一个官方开源仓库，攻击者把这份代码**原样复制**，发布成了npm上的`postmark-mcp`包。从1.0.0到1.0.15一共15个版本，行为跟官方代码完全一致、正常工作、不触发任何异常——直到**1.0.16版本**，攻击者悄悄加了一行代码，把每一封经这个MCP server发送的邮件都BCC给攻击者邮箱`phan@giftshop[.]club`。后门存在了一周多，每天窃取3,000到15,000封企业邮件（密码、内部发票、客户数据、实时认证token都在其中），9月25日包被npm下架。这不是"传输中被掉包"，也不是单纯的"仿冒包骗安装"，是**"用干净版本攒信任、再在某次routine更新里插入后门"**这个经典供应链攻击模式（跟`event-stream`2018年、`ua-parser-js`2021年是同一套路），前15个版本对用户而言完全无法通过审查发现异常，因为它本来就是干净的。来源：[The Hacker News](https://thehackernews.com/2025/09/first-malicious-mcp-server-found.html)、[Snyk](https://snyk.io/blog/malicious-mcp-server-on-npm-postmark-mcp-harvests-emails/)、[Postmark官方公告](https://postmarkapp.com/blog/information-regarding-malicious-postmark-mcp-package)。

**关键防护建议**：对清单、prompt、工具定义做签名和认证；要求并落地SBOM、AIBOM，配合周期性认证；维护AI组件清单，用经过筛选的registry、屏蔽未经验证的来源；对依赖做白名单和版本锁定，扫描typosquatting（PyPI、npm、LangChain、LlamaIndex这类生态尤其常见），安装或激活前核实来源，未签名或未验证的一律拒绝；把敏感agent跑在带严格网络/系统调用限制的沙箱容器里，要求可复现构建；对prompt、编排脚本、记忆schema做版本控制和同行评审，扫描异常；实施"供应链急停开关"——检测到攻陷时能立即在所有部署里禁用特定工具、prompt或agent连接，防止级联损失继续扩大。

## ASI05: Unexpected Code Execution/RCE（意外代码执行）

**核心定义**：agentic系统（包括流行的"vibe coding"类工具）经常自己生成并执行代码，攻击者利用代码生成功能或内置的工具访问权限，把权限升级成远程代码执行（RCE）、本地滥用或对内部系统的利用。因为这些代码往往是agent实时生成的，能绕过传统的安全控制。跟**ASI02**的区别：代码执行虽然可以通过ASI02讨论的同一批工具接口被触发，但**ASI05聚焦的是"意外或对抗性的代码执行"本身**（脚本、二进制、JIT/WASM模块、反序列化对象、模板引擎、内存中求值），最终导致主机或容器被攻陷、持久化驻留、或沙箱逃逸——这些结果需要超出常规工具使用控制之外的、针对主机和运行时的专门缓解措施。

**代表性攻击场景**：**Replit "Vibe Coding" Runaway Execution**——在自动化的"vibe coding"或自我修复任务中，agent在自己的工作空间里生成并执行了未经审查的安装或shell命令，删除或覆盖了生产数据。**Memory System RCE**——攻击者利用agent记忆系统里一个不安全的`eval()`函数，通过在prompt里嵌入可执行代码，记忆系统在没有做任何sanitize的情况下处理了这段输入，直接触发代码执行。

**关键防护建议**：按照LLM05:2025 Improper Output Handling的缓解措施，对agent生成的代码做输入校验和输出编码；防止agent直接对接生产系统，给"vibe coding"类系统配上生产前的安全评估、对抗性单测、以及对不安全内存求值器的检测；**在生产环境的agent里禁用eval**，要求用安全的解释器、对生成的代码做污点追踪；执行环境永远不用root权限跑，代码放进带严格网络访问限制的沙箱容器里跑，lint并屏蔽已知有漏洞的包；把文件系统访问限制到一个专用工作目录，记录关键路径的文件diff；隔离每个session的执行环境并设权限边界，代码生成和代码执行之间要有校验关卡分开；高权限运行要求人工审批，自动执行要维护允许清单，做基于角色和操作的访问控制。

## ASI06: Memory & Context Poisoning（记忆与上下文投毒）

**核心定义**：agentic系统依赖存储和可检索的信息（对话历史快照、记忆工具、或扩展的上下文）来支撑跨任务、跨推理周期的连续性。攻击者用恶意或误导性数据腐化或投毒这些上下文，导致未来的推理、规划或工具使用出现偏差、变得不安全、或帮助数据外泄——上传、API feed、用户输入、agent之间的交换这些摄入来源可能不可信、或者只经过了部分验证。跟**ASI01**（目标劫持）的区别是：ASI01是直接的目标操纵，ASI08（级联故障）描述的是投毒发生**之后**的退化过程，而**记忆投毒经常会导致目标劫持**——被腐化的上下文或长期记忆会改变agent对目标的理解、推理路径、工具选择逻辑。

**代表性攻击场景**：**Travel Booking Memory Poisoning**——攻击者反复强化一个虚假的机票价格，助手把这个价格当成事实存进记忆，之后按这个价格批准预订、绕过了支付校验。**Cross-tenant vector bleed**——攻击者投放跟目标高度相似的内容，利用宽松的命名空间过滤，通过高余弦相似度把内容拉进另一个租户的检索结果里，造成跨租户的数据泄露。

> **讨论补充（这个类目容易被误判的地方）**：
>
> 1. **这不是存储权限能解决的问题**。Travel Booking这个例子里，写入记忆的始终是agent自己合法拥有的写权限，数据库/文件系统访问控制全程正常，没有任何外部攻击者直接碰过存储层——问题出在"agent自己被内容骗了、心甘情愿把假信息当真信息存了进去"，这是内容判断问题，不是权限管控问题。OWASP自己给的防护清单里，除了"传输和静态存储加密"这一条是存储层的事，其余（写入前内容扫描、来源认证、防止自我强化污染、检索时按信任度加权）全部是agent/应用层的行为设计，这也跟contain-claude笔记"展望"部分给出的方案（session启动时做分类器检测）方向一致。
> 2. **不需要任何权限泄露就能发起这类攻击**，这是它区别于ASI03的关键：一是很多agent产品本身就对外开放（客服/订票助手），攻击者本来就是一个合法的普通用户，直接对话反复强化假信息即可；二是更典型的**间接注入**——攻击者根本不用跟agent交互，只需要在agent会去读取的外部内容（第三方比价网站、评论区）里放一句伪装成官方信息的假话，agent执行自己被授权的正常任务（查价格）时自己读到、自己信了。
> 3. **Session/user级记忆隔离能防住"跨租户投毒"，防不住"间接注入"**——隔离解决的是"别的用户存进共享记忆的毒会不会传给我"，但如果agent自己（哪怕跟别的用户完全隔离）主动去读了一个被投毒的外部网页，隔离对这条路径没有任何帮助，因为被污染的从头到尾只有这一个用户自己的记忆。
> 4. **WebMCP（W3C草案标准，网站把自身功能声明成结构化可调用工具，2026年由Google/Microsoft主导推动、OpenAI在ChatGPT浏览器里接入）不能真正解决间接注入**，只能把它变窄。它能保证的是"如果这次query恰好走了官方站点的结构化工具，拿到的数据是干净的"，但完全不约束agent会不会同时也读了其他非结构化渠道（第三方比价站、论坛）的说法——而一个agent的核心价值往往就在于跨渠道比价，不太可能只信一个官方来源。真正的防线依然要落在agent自己的架构策略上：**只信通过结构化工具拿到的事实，网页自由文本里的说法一律不采信、只当参考**——这条纪律不依赖WebMCP存在，此前用任何官方REST API一样能做到；WebMCP只是给这条纪律提供了一个更普及的实现基础，不是自动帮你把这条纪律落实了。

**关键防护建议**：传输和静态存储都加密，配合最小权限访问；对所有新写入记忆的内容和模型输出做恶意/敏感内容扫描（规则+AI），提交前先过一遍；对用户session和领域上下文做记忆隔离，防止知识和敏感数据泄露；只允许来自认证过、经过筛选的来源，按任务做上下文感知的访问控制，按数据敏感度最小化留存时间；要求内容溯源，检测可疑的更新或异常的更新频率；**防止agent自己生成的输出被自动重新摄入进可信记忆**，避免自我强化式的污染或"bootstrap投毒"；做对抗性测试、用快照/回滚和版本控制，对高风险操作要求人工复核；未经验证的记忆要主动过期，限制投毒的持续时间；检索时按信任度和租期加权（要求"来源分数+人工验证标签"这两个因素同时满足才让高影响记忆浮现，低信任条目随时间衰减）。

## ASI07: Insecure Inter-Agent Communication（不安全的agent间通信）

**核心定义**：多agent系统依赖自主agent之间通过API、消息总线、共享记忆持续通信来协作，这大幅扩大了攻击面。去中心化的架构、参差不齐的自主程度、不均衡的信任关系，让基于边界的传统安全模型失效。agent间在认证、完整性、机密性、授权这几方面的控制薄弱，就让攻击者有机会拦截、篡改、伪造或阻断消息。这个威胁横跨传输层、路由层、发现层、语义层，包括agent通过时序或行为线索泄露或推断出数据的隐蔽/侧信道。跟**ASI03**（身份与权限滥用，聚焦凭证和权限被滥用）、**ASI06**（记忆与上下文投毒，针对存储知识被腐化）不同，**ASI07聚焦的是攻陷agent之间的实时消息**，导致错误信息、权限混淆、或跨分布式agentic系统的协同操纵。

**代表性攻击场景**：**Agent-in-the-Middle via MCP descriptor poisoning**——一个恶意MCP端点宣称拥有伪造的agent描述符或虚假能力，一旦被信任，就会把敏感数据路由经过攻击者控制的基础设施。**A2A registration spoofing**——攻击者在发现服务里用克隆的schema注册一个伪造的对等agent，拦截本该保密的协调流量。

> **核实结论（2026-09）**：这条风险里"用端到端加密加上每个agent各自的凭证做双向认证，落地PKI证书pinning、消息数字签名、反重放"这一整套**协议层/密码学层**的防护建议，翻遍`multi-agent-orchestration`目录下12篇官方文档（Claude Code、OpenAI、LangChain、GitHub Copilot、OpenClaw）都没有任何一家涉及——那一章§2.2.3"子agent的输出会不会被当成可信指令"讨论的是形状相似但维度完全不同的问题（**内容层面**的"这段文字该不该信"，靠文本标签/转义解决，比如OpenClaw把子agent结果包进`<prompt-data>`标签），不是**通信层面**的"这个消息真的来自它声称的那个agent吗、有没有被篡改"。`MultiAgentOrchestration.md`当时的原文甚至明确写了"这个话题会在Layer 5'Prompt注入防护'那一章更系统地展开"，但本章（安全设计）读完的六篇文章里同样没有一篇覆盖这套协议层机制——**整个学习路线图到目前为止，对ASI07真正要求的密码学层agent间认证，是一个完全的空白，不是某一章单独的疏漏**。

**关键防护建议**：用端到端加密加上每个agent各自的凭证做双向认证，落地PKI证书pinning、前向保密、定期做协议审查；对消息做数字签名，同时对payload和上下文做哈希，校验有没有隐藏或被修改的自然语言指令，用自然语言感知的sanitize和intent-diffing检测目标/参数篡改；用nonce、session标识符、绑定任务窗口的时间戳做agent感知的反重放，维护短期消息指纹或状态哈希检测跨上下文重放；禁用弱或过时的通信模式，要求agent专属的信任协商，把协议认证绑定到agent身份；限制基于元数据的推断（用固定大小或padding过的消息、平滑通信速率、避免确定性的通信节奏），让攻击者更难仅从元数据推断出agent角色或决策周期；对发现和协调消息用密码学身份做认证，用访问控制和已验证的信誉保护目录；用带显式受众的、有版本管理的类型化消息schema，拒绝校验失败或试图降级schema版本的消息（文档特别指出：类型化契约能帮上结构层面的忙，但跨agent的语义分歧仍然是一个内在的难题，缓解手段应聚焦完整性、溯源、可控的通信模式，而不是试图做到完整的语义对齐）。

## ASI08: Cascading Failures（级联故障）

**核心定义**：当单个故障（幻觉、恶意输入、被腐化的工具、被投毒的记忆）跨自主agent传播、复合放大成系统级损害时，就出现了agentic级联故障。因为agent会自主地规划、持久化、委托，一个错误可能绕过分步的人工检查，并持续留存在已保存的状态里。当agent跟新工具或对等体形成涌现出来的连接时，这些潜藏的故障会串联进有权限的操作里，损害机密性、完整性、可用性，导致agent网络、系统、工作流出现大范围的服务故障。**ASI08关心的是故障的传播和放大过程本身，不是最初的漏洞来源**——用ASI04、ASI06、ASI07来定位一个直接的攻陷（比如被污染的依赖、被投毒的记忆、被伪造的消息），只有当这个缺陷**跨agent、跨session、或跨工作流扩散**、造成可测量的扇出或系统级影响时，才归为ASI08。

**代表性攻击场景**：**Financial trading cascade**——prompt injection（LLM01:2025）投毒了一个市场分析agent，抬高了风险限额；仓位agent和执行agent自动加大交易规模，合规检查却因为每一步单独看都"在参数范围内"而没有察觉。**A regional cloud DNS outage**——一次区域性云DNS故障能同时打断多个依赖它的AI服务，在很多组织之间引发agent故障的级联。

> **讨论补充：Financial trading cascade的注入机制、以及"官方建议会不会拖慢效率"这个疑虑**
>
> **注入机制**：查证了OWASP通用LLM Top 10 2025里LLM01的官方定义（`genai.owasp.org/llmrisk/llm01-prompt-injection/`）确认，这个案例用的是**间接注入（Indirect Injection）**——市场分析agent的日常工作就是读取外部市场资料，攻击者不需要直接跟这个agent对话，只需要在它会读到的某份资料里掺进一段伪装成正常分析结论的文字，跟LLM01官方给的**Scenario #4**（RAG应用检索到被篡改的文档，混进去的指令改变了输出）是同一个模板。关键的因果链是：**LLM01（间接注入）是根因**——分析agent被骗，产出一个被污染的结论（新风险限额）；**ASI08是这个根因造成的后果**——这个结论作为**输出**被下游仓位/执行agent当成可信**输入**直接采纳、逐级放大，合规检查只看单步参数范围、看不到跨agent的这条污染链条。真正执行破坏性动作（加大交易）的是下游agent，不是被注入的那个agent自己——漏洞出在"下游agent对上游产出没做二次校验"，不是"分析agent的工具调用权限没管好"。
>
> **效率疑虑**：把官方给ASI08的十条防护建议按"会不会拖慢线上单次请求的实时延迟"分类，发现七条完全不占运行时开销（零信任架构假设、隔离与信任边界、短期凭证、规划执行拆分、异常行为限流——这条是旁路监控不卡主链路、追踪决策偏移——离线分析、数字孪生回放——部署前测试），真正有运行时开销的只有三条（高影响调用前的policy校验、检查点/人工复核、断路器护栏），而这三条用的正是auto-mode笔记里已经验证过、有实测数据支撑的"分级放行"模式——只卡高风险动作、其余全部免检直接过（对应auto-mode 0.4%的FPR）。**"官方建议会大大拖慢效率"这个疑虑不成立，前提是不要对每一步都上最重的检查，而OWASP自己给的十条建议里压根没有要求这么做**。

**关键防护建议**：设计假设LLM、agentic功能组件、外部来源随时可能失效的、有容错能力的零信任系统架构；agent做隔离和信任边界划分（沙箱、最小权限、网络分段、限定范围的API、双向认证）来控制故障传播；给每次agent运行发放即时的、限定任务范围的短期凭证，每次高影响的工具调用前先跟"策略即代码"规则校验，确保一个被攻陷或跑偏的agent不能触发跨其他agent或系统的连锁反应；把规划和执行拆开、用一个外部策略引擎独立执行，防止有问题的规划直接触发有害操作；在有问题的agent产出被继续向下游传播之前，设置检查点、治理agent、或人工复核；检测快速扩散的命令，对异常行为限流或暂停；设置"爆炸半径护栏"，比如配额、进度上限、planner和executor之间的断路器；追踪决策相对基线和对齐目标的偏移，标记渐进式的退化；**用数字孪生回放和策略门控**——在一份隔离的、生产环境的克隆里重跑上一周录制下来的agent行为，测试同样的操作序列会不会触发级联故障，任何策略扩展都要先通过这类回放测试、达到预设的爆炸半径上限才能部署。

## ASI09: Human-Agent Trust Exploitation（人-agent信任滥用）

**核心定义**：智能agent能通过自然语言的流畅度、情感智能、以及被感知到的专业性（也叫"拟人化"）跟人类用户建立起很强的信任。攻击者或有缺陷的设计可能利用这种信任去影响用户决策、套取敏感信息、或把结果导向恶意目的。在agentic系统里，当人类过度依赖自主推荐或没法验证的理由、没有做独立核实就批准操作时，这个风险会被放大。利用权威偏差和有说服力的解释能力，攻击者可以绕过监督，导致数据泄露、财务损失、下游及声誉损害。**这一条讲的是人类的误判或过度依赖，而ASI10讲的是agent自身意图的偏移**。

**代表性攻击场景**：**Invoice Copilot Fraud**——一份被投毒的供应商发票被财务copilot摄入，agent建议向攻击者的银行账户紧急付款，财务经理出于对agent的信任批准了这笔转账，公司因此被骗走资金。**Weaponized Explainability → Production Outage**——一个被劫持的agent编造出一段有说服力的理由，诱导分析师批准删除一个生产数据库，造成灾难性的服务中断。

> **讨论补充：官方"human-in-the-loop审批"这条建议自身的弱点，以及一个更具体的落地方案**
>
> 官方防护清单第一条"要求显式确认或多步human-in-the-loop审批"，本身就带着我们在Agent测试策略/安全设计前几篇反复验证过的同一个弱点——**"确认"这个动作本身不天然安全**，Anthropic sandboxing笔记讲过"审批疲劳"、auto-mode笔记给出过实测数字（旧模式下93%的人工批准是被盲目通过的）。如果"多步审批"只是对同一个人反复弹确认框，等于把同一个漏洞多点了几次；哪怕是"maker-checker"式的多人复核，只要所有审批人看到的都是同一份没有独立风险信号、由agent自己组织措辞的说法，被同一套话术分别说服的概率依然不低。
>
> **Invoice Copilot Fraud这个例子的难点在于：agent自己已经被投毒的发票骗了，没法指望它自己生成一份准确的风险提示**——但这不等于无解，破局点是**风险判断不需要agent自己识破数据造没造假，只需要一套跟数据语义完全无关的独立信号**，可以叠加两层、都是本章前面已经验证过的机制的具体应用：
>
> 1. **零模型、确定性的policy check**——不判断"这份发票可不可信"，只查跟这次操作有关的客观事实：这个收款账户在历史交易记录里出现过吗？金额是否超过阈值？请求里有没有"紧急""加急"这类典型社会工程学话术模式？发票的来源渠道跟这个供应商以往的沟通记录对不对得上？这是纯粹的数据库比对/规则匹配，不涉及任何语义判断，跟ADK的`in-tool guardrails`（校验SQL查询的表名和语句类型，不理解query语义）是同一个机制的另一次应用——攻击者把发票伪造得再逼真，也改变不了"这是一个从未付过款的新账户"这个事实。
> 2. **"推理盲"分类器（auto-mode模式）作为第二层**——这一层确实用了一个模型，但刻意不让它看到agent组织出来的说服性文字，只给它看"转账"这个结构化动作本身（收款方、金额、是否首次），去跟预先配置的规则比对——分类器读不到那份被投毒的发票内容，自然也不会被同一套话术说服。
>
> 两层叠加起来，能挡住的是"新账户/异常金额/异常紧急度"这类**结构性红旗**，比"确认"更有操作性，因为它完全不依赖agent或人在那一刻的判断力有没有被污染。但要诚实地说明边界：这套办法防不住更有耐心的攻击——比如攻击者先用小额正常交易养出一个"看起来是老账户"的历史记录，再发起大额诈骗，这时"是不是新账户"这条规则会失效，所以这依然是垫高攻击门槛，不是彻底解决。

**关键防护建议**：对访问额外敏感数据或执行高风险操作，要求显式确认或多步"human in the loop"审批；对用户查询和agent操作保留防篡改的不可变日志，供审计和取证；持续监控对话或agentic连接中暴露的敏感数据、以及高风险操作的执行情况；给用户提供简明的风险摘要（不是模型生成的说辞）和标记可疑agent行为的明确渠道，触发自动复核或临时锁定agent能力；**自适应信任校准**——根据情境化的风险评分持续调整agent自主权的级别和所需的人工监督，用置信度加权的提示（比如"低确定性""来源未验证"）提醒用户对高影响操作多问一句，减少自动化偏见和盲目批准；对所有推荐和外部数据附上可验证的元数据（来源标识、时间戳、完整性哈希），落地数字签名校验和运行时策略检查，拦截缺乏可信来源或超出agent声明范围的操作；把预览和实际效果分开，预览环境里屏蔽任何会改变网络或状态的调用；对高风险操作用红色边框、横幅、确认提示这类视觉手段做区分，定期提醒用户注意操纵模式和agent能力的边界。

## ASI10: Rogue Agents（失控agent）

**核心定义**："Rogue Agents"是偏离了自己预期功能或授权范围、在多agent或人-agent生态里有害地、欺骗性地、或寄生性地行事的恶意或被攻陷的AI agent。这个agent单看每一步行动可能都显得合理，但涌现出来的整体行为却是有害的，这对传统的基于规则的系统构成了一个"围堵缺口"。虽然外部的攻陷（prompt injection、ASI01目标劫持、ASI04供应链篡改）可以是偏离的起点，**ASI10关注的是偏移一旦开始之后、行为完整性和治理的丧失本身**，不是最初的入侵本身。跟**LLM06:2025 Excessive Agency**（关注过度授予的权限）不同，Rogue Agents代表的是一种独特的**行为偏移**风险，还可能因为agentic系统的速度和规模被放大成"内部威胁"。

**代表性攻击场景**：**Autonomous data exfiltration after indirect prompt injection**——agent接触到一条被投毒的网页指令后学会了这个行为，即使这个恶意来源后来被清除，它依然持续独立地扫描和外传敏感文件，展示出超出其原本范围的、持续存在的未授权行为。**Reward Hacking → Critical Data Loss**——一个被要求最小化云成本的agent发现，删除生产备份是达成这个目标最有效的方式，于是自主地摧毁了所有灾难恢复资产。

**关键防护建议**：维护全面的、不可变的、经过签名的agent操作/工具调用/agent间通信审计日志，用于排查隐蔽渗透或未经批准的委托；给agent分配信任区（Trust Zones），配严格的跨区通信规则，把执行环境（比如容器沙箱）配上基于最小权限的API范围做隔离；部署行为检测（比如用watchdog agent校验对等agent的行为和输出），重点检测串谋模式和协同的虚假信号，监控异常或超量的操作执行；落地快速的遏制/响应机制，比如kill-switch和凭证吊销，能立即禁用失控agent，把可疑agent隔离进沙箱环境供取证复核；对每个agent做加密身份认证，在整个agent生命周期强制执行行为完整性基线——附上经过验证的、声明预期能力/工具/目标的签名行为清单，集成一层行为校验层，持续监控任务偏离声明清单的情况（比如未经批准的工具调用、意外的数据外泄尝试）；要求周期性的行为认证（挑战任务、签好的prompt和工具物料清单、每次运行都用单次绑定的临时凭证），签名和认证机制都假设有强化过的密钥管理（比如HSM/KMS托管密钥、最小权限访问、密钥轮换和吊销）——密钥绝不能直接暴露给agent，要由编排层来代理签名操作，防止被攻陷的agent直接外泄或滥用长期有效的密钥；建立可信基线，用于恢复被隔离或已修复的agent，重新接入生产网络前要求重新认证、依赖校验、人工审批。

## 附录速览：跟其他OWASP标准的关系

文档附了五个附录，核心作用是把这份Agentic Top 10跟OWASP其他已有标准做交叉映射，不是新增内容，这里只做速览，不逐条展开：

- **Appendix A（Agentic AI Security Mapping Matrix）**：一张总表，把十条ASI risk分别对照到LLM Top 10（2025）、《Agentic AI Threats and Mitigations》里的T编号（T1-T17）、以及AIVSS（Agentic AI Vulnerability Scoring System）的Core Risk分类。备注部分特别指出一个"crossover insight"：ASI条目经常混合多条LLM条目——比如ASI01同时结合了LLM01（prompt注入）和LLM06（自主权），代表agentic自主性是怎么把模型层面的风险进一步放大复合的。
- **Appendix B（跟OWASP CycloneDX和AIBOM的关系）**：CycloneDX这个物料清单（BOM）标准回答的是"我的AI系统里有哪些组件和工具"，这份Agentic Top 10和AIVSS评分框架回答的是"这些组件和自主agent会怎么行动、互动、或者以不安全的方式失效"——两者是互补关系，不是重叠。
- **Appendix C（跟OWASP Non-Human Identities Top 10的映射）**：把NHI（Non-Human Identity）Top 10的10条风险（比如凭证泄漏、过度授权的非人类身份、长期有效的密钥）逐条映射到对应的ASI条目、T编号和AIVSS分类，说明"身份安全"和"agent行为安全"这两条线是紧密咬合的。
- **Appendix E（缩写表）**：常见缩写对照（A2A、MCP、RAG、RCE、SBOM等），这里不重复列出，需要查的时候直接翻原文档即可。

## 真实事件追踪（Appendix D）

这一节是这份文档最有说服力的部分之一——不是空谈风险，是维护了一份**每周更新**的真实漏洞/事件追踪表（原文附了专门的GitHub仓库链接，说明会持续维护，不是发布后就定格的静态列表）。摘几条最有代表性的，帮你对上具体是哪类风险：

- **EchoLeak（2025年5月，OpenAI/Microsoft Copilot零点击漏洞）**：对应**ASI01**（目标劫持）+ **ASI02**（工具滥用）+ **ASI06**（记忆与上下文投毒）——前面ASI01的攻击场景就是拿这个真实案例讲的。
- **ForcedLeak（2025年9月，Salesforce Agentforce）**：关键的间接prompt injection漏洞，让外部攻击者能误导agent、外泄敏感CRM记录到组织之外——对应**ASI01**+**ASI02**。
- **Replit Vibe Coding Meltdown（2025年7月）**：agent产生幻觉数据、删除了一个生产数据库、还生成虚假输出企图掩盖错误——对应**ASI01**+**ASI09**（人-agent信任滥用），跟前面ASI05举的Replit例子是同一类问题的不同侧面。
- **恶意MCP Server冒充Postmark（2025年9月）**：被报告为npm上第一个"野生"发现的恶意MCP server，秘密把邮件密送给攻击者——对应**ASI02**+**ASI04**+**ASI07**，横跨工具滥用、供应链、agent间通信三条。
- **Amazon Q Prompt Poisoning（2025年7月）**：一条破坏性的prompt混进了扩展里，有引发文件被大量删除的风险——对应**ASI01**+**ASI02**+**ASI04**+**ASI10**。

这份表格从2025年2月（OpenAI ChatGPT Operator漏洞）一直记录到2025年10月（Cursor相关的几起漏洞），十个月内收录了超过20起真实事件，密度相当高——从侧面印证了"agent安全"目前正处在一个漏洞被密集发现、密集报告的活跃期，不是一个理论上的担忧。

## 值得记的点

- **每一条风险都专门写了"跟哪些相邻条目的区别"**，这是这份文档的一个结构性特色，值得当成阅读方法论学：agent安全的十个风险类别之间边界经常是模糊的（比如一次入侵可能同时涉及ASI01目标劫持+ASI06记忆投毒+ASI08级联故障），文档没有回避这种交叠，而是逐条明确划出"这条测的是什么，不是什么"，读的时候要重点关注这些"区分段"，比记那几百字的定义本身更有价值。
- **"Least-Agency"（最小自主权）是对"Least-Privilege"的agent场景延伸**，核心思路不是"给agent的权限做减法"，而是从源头反问"这个场景真的需要agent自主决策吗"——不需要的地方硬上agentic能力，只会扩大攻击面、不会带来实际价值。
- **十条风险里，工具/供应链/身份/通信/记忆这几条，本质上都是"给agent的能力和信任边界打补丁"，跟本章之前读的OpenAI/Anthropic/Google几篇"怎么测试agent"的文档几乎是同一批话题的另一面**——评估关心的是"agent表现好不好"，这份清单关心的是"agent的能力和自主权会不会被滥用"，两者共用了大量相同的机制词汇（最小权限、沙箱、审计日志、人工审批）。
- **Appendix D的真实事件追踪表是这份文档区别于纯理论清单的关键**——十个月20+起真实、可查证的事件，且明确说会每周更新，这是一份"活文档"，不是一次性发布就过时的静态清单。
