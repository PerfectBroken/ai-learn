# Restart recovery（OpenClaw）

来源：`docs.openclaw.ai/gateway/restart-recovery`

## 核心结论

Gateway重启不会丢agent状态——对话、transcript、定时任务、后台任务记录、排队的出站消息全部落盘，跑到一半被打断的工作，Gateway重新起来之后会自动检测并恢复。恢复默认是常开的，正常情况不需要人工介入；只有"基础设施重试次数耗尽"或者"缺少一个持久化的消息-动作权限声明"这两种情况，会把某个session单独隔离出来，等人工检查或替换。

### 什么东西能扛过重启

| 状态 | 存在哪 | 重启之后的行为 |
|---|---|---|
| 对话历史 | 每个agent自己的SQLite数据库 | 原封不动，session接着存下来的transcript继续 |
| 被打断的主session轮次 | 每个agent的SQLite session行+transcript | 启动几秒钟后自动恢复或者reconcile |
| 子agent运行 | SQLite（共享状态数据库） | 启动时恢复registry，被打断的运行接着跑 |
| 后台任务 | SQLite（共享状态数据库） | 启动时reconcile，孤儿任务被恢复或标记为丢失 |
| 排队中的出站投递 | SQLite投递队列 | 重启后排空，没投递成功的重试 |
| 定时（cron）任务 | SQLite cron store | 计划保留，调度器启动时重新武装 |
| 重启续接 | SQLite重启哨兵 | 一次性的续接消息，发给请求重启的那个session |
| Gateway终端PTY | 进程内存 | 跟旧进程一起结束，终端session不会被恢复 |

排队中的投递行会在重启后排空或重试；失败的行会丢弃payload，只有"可复用"或者"崩溃时状态不明确"的所有者，才会保留一份最小化的、有边界的或者永久的收据，防止重复投递。

## 优雅重启：先排空再关

主动请求的重启（`openclaw gateway restart`、需要重启的配置变更、Gateway升级）不会立刻杀掉正在跑的工作。Gateway先停止接受新工作，然后等活跃的agent轮次和后台任务跑完，最多等一个"排空预算"（默认5分钟）。**所以大部分重启其实什么都不会打断。**

只有排空预算内跑不完的工作（或者被强制重启/崩溃打断的任何运行）才会被中止——而且中止之前，受影响的每个session都会先被标记为"待恢复"。

## 主机休眠 / 进程冻结

Gateway主机从睡眠唤醒、虚拟机恢复、或者进程在长时间暂停后继续跑，Gateway大概30秒内就能检测到这次"冻结"，重启channel连接、刷新缓存的健康状态和在线状态，让客户端不用等着过期的socket或快照超时。

macOS app和Linux companion会在主机睡眠前跟本地Gateway配合，准备一个短暂的"暂停租约"，唤醒后再恢复；远程Gateway在app所在主机睡眠时不会被暂停。通过`gateway.suspend.*`主动挂起的情况，恢复会被推迟到controller显式恢复Gateway为止。

## 怎么检测到"跑到一半被打断"的工作——三种互补机制

- **接纳轮次的时候**：对一个已有主session上的普通文本轮次，Gateway会在**同一个SQLite事务**里完成三件事——追加用户消息、把session标记为running、记录它的恢复投递声明——这一步发生在模型或`before_agent_reply`钩子执行**之前**。Control UI在返回`started`确认之前做这件事；channel dispatch在准备好的轮次接管agent运行时做这件事。（命令、附件、单轮覆盖项、待处理投递、之前的中止提示、插件own的session、带执行钩子的轮次，各自走专门的接纳路径。）如果装了`before_agent_reply`钩子，接纳阶段会记下足够的阶段状态，用来区分"一次已完成的静默结果"和"一个含糊不清的副作用窗口"。恢复会派发一次普通的、用户触发式的agent轮次，所以当前加载的`before_agent_reply`钩子会按正常的触发规则跑；含糊不清的钩子结果，恢复时只会用"重启安全"的工具，而不是重放不受限制的副作用。
- **关闭的时候**：排空重启期间，每一个还有活跃运行的session，在运行被中止**之前**，都会在session存储里打上一个恢复标记。
- **启动的时候**：Gateway会扫描session存储，找那些还自称"running"、但在新进程里找不到活着的所有者的session——这能抓住那种没跑完任何关闭代码的硬崩溃/被kill的情况，同时清理过期的transcript锁文件。

## 自动恢复怎么发生的

启动几秒钟后，Gateway会给每个被标记的session重新派发一条合成的系统消息，告诉agent"你上一轮被重启打断了，接着现有的transcript继续"。如果之前已经生成了最终回复但没投递出去，回复文本会被一起带上，agent可以直接投递它，不用重做一遍。

- **启动时的reconciliation**：瞬时失败最多重试三次，指数退避。
- **每个被打断的主session周期，有一个独立的、持久化的预算**：三次"计费"的自动派发尝试，跨Gateway重启保留。OpenClaw在派发之前先扣一次预算，如果Gateway在接受请求之前明确拒绝了，就退还这次预算；如果派发之后的结果不确定，就保留这次扣费，避免重放工作。已经own了这个session的前台工作，会让自动恢复暂缓，直到那个前台工作自己收尾。
- **预算耗尽之后**：session会被"打上墓碑标记"（tombstoned），而不是无限循环重试。要检查失败的session，用`/new`或`/reset`起一个替代session。`openclaw doctor --fix`能修复一个跟墓碑标记冲突的、过期的中止标记，但**不会**重新激活那一轮恢复循环。
- **去重保证**：每次重试都复用同一个持久化的派发标识符，所以一次含糊不清的连接失败不会把同一次恢复启动两遍。已完成的Control UI轮次也保留了有边界的持久化幂等墓碑，让一个重新连上的outbox能"退役"它们、不会重新执行请求。
- **纯消息工具类回复的恢复，走第二套持久化关联机制**：在一次终态的、同一对话内的发送真正到达channel之前，Gateway会针对这个精确的session和源轮次记录一个"未解决的投递意图"；provider确认成功，就把它解析成一个持久化的"已投递"收据；provider确认失败，就清掉它。恢复流程只补一个"已投递"收据，不会重跑工具。如果一次崩溃导致provider的结果不明确，恢复会改用"重启安全"的工具继续，让模型能检查并汇报这个不确定性，而不是重放外部副作用。
- 投递成功的回复也会连同它的源消息ID一起镜像进transcript；终态镜像用独立的收据key，避免跟同一个provider幂等key下的进度型发送互相冲突；只有持久化的channel-ingress声明才能恢复"消息-动作权限"。一次恢复运行会保留原始的源投递模式和源关联（包括请求者身份、同频道/同线程限制），确保即便恢复过程中再来一次重启，同一份收据依然有效。**一个没法重建channel权限的、纯消息工具类的轮次，会被直接打上墓碑标记**——因为OpenClaw没法在缺少原始channel-ingress声明的情况下，安全地凭空铸造"消息-动作权限"。终端提示会引导用户用`/new`或`/reset`开一个替代session。

**恢复前会先给transcript尾部分类，决定续接时该用什么工具限制**：一次被中止的轮次，中断本身就是"中止"这件事——恢复会尽力按provider或worker记录下的中止细节续接：流式输出到一半的文本保留在transcript里，续接从它下面那条消息继续；一个悬空的工具调用会从下一次provider payload里剔除，并限制成只能用"重启安全"的工具，除非它被审计确认为"可安全重放"。Provider失败、已完成的assistant尾部、空transcript、过期的待批准请求，也都从现有transcript继续。有歧义副作用的状态用"重启安全"工具；其余情况由模型自己判断"哪些已经完成、哪些还没"，可以把不确定性汇报给用户。

OpenClaw也能重建被打断的、只读的Code Mode工作——这类运行会被标记为"重启安全"，涉及副作用的catalog/namespace工具调用会在执行前被拒绝。如果重启正好落在`wait`这个控制点上，新Gateway会从transcript重建这个轮次，并强制重建出来的执行保持"重启安全"，哪怕模型本身省略或清掉了这个标记。宿主会把整个重建出来的轮次过滤成只允许"审计过的只读核心工具"和"明确标记为可安全重放的插件工具"，哪怕重启之后Code Mode已经被关掉了。一个不可安全重放、或者匹配不上的Code Mode检查点，依然会恢复给模型做reconciliation，但不带Code Mode控制、并且限制成"重启安全"工具。

### 子agent

子agent的运行持久化在共享的SQLite状态数据库里，所以registry能扛过进程重启。启动时registry被恢复，被打断的子agent session带着原始任务上下文恢复。两个安全阀：

- **超过2小时前被打断的运行，直接终结，不会被恢复**——避免一个宕机一整晚的Gateway把陈旧的工作复活。
- **反复恢复失败的session，会被打上"卡死"（wedged）的墓碑标记**，避免恢复无限循环。

### 后台任务

后台任务registry是SQLite支撑的，启动时和周期性间隔都会reconcile：已完成运行记录的持久化结果会被恢复；owning进程消失了的运行，在一个宽限期之后会被标记为"丢失"，而不是永远挂着。

### Agent自己触发的重启

当agent自己触发一次重启（应用配置变更、更新Gateway、或者显式的重启请求），进程退出前会往SQLite写一个重启哨兵。启动之后，Gateway把结果发回原始聊天，并派发一次一次性的续接轮次，让agent正好从它离开的地方接着来，在同一个channel和线程里。

哨兵的类型化SQLite列是重启处理的权威数据源；它的`payload_json`值只是一个用于重放/调试的影子数据。运行时读写清空SQLite状态，没有文件回退路径。存储切换期间，启动时和跑Doctor时会做一次有边界的状态迁移，用来保留旧进程升级后留下的、经过校验的`restart-sentinel.json`；迁移会校验这个类型化的行，并在正常重启处理继续之前删掉源文件。

## 安全阀与可观测性

- **崩溃循环断路器（Crash-loop breaker）**：5分钟内3次不干净的启动，会触发一个断路器，抑制下一次启动时自动拉起的旁路服务（比如channel插件），避免一个不断崩溃的Gateway把自己的问题放大。一个持续稳定的安全模式Gateway，会在整个"不干净启动窗口"排空之后重新检查这个断路器，然后恢复被推迟的channel自动启动，不需要再手动重启一次Gateway。断路器触发时，**控制平面依然会启动**，但channel插件（以及其他自动启动的旁路服务）会保持关闭，直到运维人员手动覆盖这个抑制、或者整个窗口排空且期间没有再出现不干净启动。恢复会保留运维人员手动停掉的channel，以及任何单独的开发模式抑制设置。
- **主session尝试预算**：每个被打断的周期三次计费的自动派发尝试；耗尽之后把那个session打上墓碑标记，直到被检查和替换。
- **指标（Metrics）**：恢复活动通过Prometheus导出为`openclaw_session_recovery_total`和`openclaw_session_recovery_age_seconds`。
- **日志**：恢复决策记在`main-session-restart-recovery`和`subagent-interrupted-resume`这两个子系统下面。
- **回复钩子**：被恢复的轮次会按正常的用户触发规则跑当前加载的`before_agent_reply`钩子；自动投递的回复在发到channel之前，也会跑正常的`reply_payload_sending`钩子，带着恢复出来的session、运行、账户、对话上下文。

## 哪些东西不会被恢复

- 因为已经有别的owner在管，被排除在主session恢复之外的session：子agent session（走子agent恢复那条路）、cron session（调度器按计划重跑）、ACP管理的session（连接的IDE/客户端自己负责恢复）。
- 从来没被接纳过的工作：排空窗口期间到达的消息，会收到一个明确的重启错误，而不是被悄悄排进一个正在死掉的进程里。
- Gateway终端PTY，包括运维和agent own的终端——它们是进程本地的，Gateway重启就结束了。
- 独立的embedded轮次，没法接管一个还有待处理重启恢复的主session，因为它们不共享Gateway的生命周期所有者——要么通过Gateway跑这个轮次，要么在Gateway那边用`/new`或`/reset`重置它。

## 值得记的点

- **这篇比"重启后session能不能恢复"这个标题范围大得多**——真正的重心是"OpenClaw怎么保证恢复不会重复执行/不会丢失外部副作用"，`activeWriterRunId`/`expectedWriterRunId`/持久化派发标识符/"消息-动作权限"这几套机制，都是为了在"崩溃时机不确定"这个前提下做到**幂等**，比另外四家笔记里讨论的"能不能恢复对话"这个层面深了一整层。
- **有一个专门的"预算"概念（三次计费的自动派发尝试），耗尽就墓碑化，不会无限重试**——这跟另外四家都没有对应的机制；LangGraph/OpenAI/Claude/Copilot的笔记里都没有讨论过"自动恢复失败次数上限"这个话题。
- **子agent恢复有一个"2小时窗口"的安全阀**，超过这个窗口的中断运行直接终结不恢复——这是一个具体的、之前没在任何一家笔记里见过的时间阈值。
- **优雅重启(graceful restart)和强制中断是两条不同的路径，前者默认5分钟排空预算、大部分时候什么都不会打断**——这个"重启不一定等于中断"的区分，另外四家的笔记里都没有专门讨论过（都是默认"重启=需要恢复"）。
